\section{Arquitectura general del sistema}
A diferencia de las tecnologías pasadas, 5G está diseñada para ser fácilmente desplegada en entornos virtualizados y basados en contenedores, lo que permite una mayor flexibilidad y escalabilidad. En este proyecto, se ha implementado un entorno de desarrollo que emula una red 5G Standalone (SA), virtualizando sus componentes principales mediante Docker y orquestando el Core con Docker Compose.
El entorno de desarrollo se ha desplegado utilizando GNS3 \cite{gns3}, GNS3 VM y VMware Workstation para crear una infraestructura base o underlay sobre la cual se han implementado otras máquinas virtuales  que alojan los contenedores Docker. Esta infraestructura virtual proporciona la conectividad necesaria entre los componentes y permite emular una red de un MNO (Mobile Network Operator) real, con componentes tanto de red y VFs (Virtualized Functions) como de 5G. También cabe destacar que para los componentes de 5G se empleó el proyecto open source free5gc \cite{free5gc,huang2021free5gc}, el cual permite desplegar un core 5G SA completo en un entorno virtualizado con Docker. La siguiente figura muestra la arquitectura general del entorno de desarrollo implementado, destacando la integración entre GNS3, Docker y la máquina virtual en vmware \ref{fig:diseno_sistema}.

\subsection{Diseño de la red 5G SA}
Con respecto a la red de transporte, se ha implementado utilizando switches programables P4 para insertar metadatos de telemetría en banda (INT-MD) en el tráfico N2 (SCTP) y N3 (GTP-U), estos switches están construidos con P4 para el reenvío de tráfico a nivel de L3. Además de estos switches P4, tanto para el tráfico entre los Nodos en el Core como en la comunicación entre el NGRAN y R1, se ha empleado switches virtuales Open vSwitch (OVS) para gestionar los paquetes ARP. \section{Despliegue del Core 5G SA}
Como se pudo apreciar en la figura \ref{fig:diseno_sistema}, el Core 5G SA se ha desplegado utilizando contenedores Docker orquestados con Docker Compose dentro de máquinas virtuales alojadas en una máquina virtual principal (GNS3 VM). Los componentes que interactúan mediante HTTP/2 se han desplegado en una VM con Ubuntu 20.04, mientras que el resto de componentes; AMF, SMF y UPF se han desplegado en máquinas virtuales separadas con la misma versión de Ubuntu. Juntar los componentes que interactúan mediante HTTP/2 en una sola VM permite reducir la latencia y mejorar el rendimiento de las comunicaciones entre ellos.

La configuración de red de cada contenedor Docker se realizó con la modalidad de red \textbf{macvlan}, detallada en la tabla \ref{tab:lld_containers}, que permite asignar una dirección IP en el mismo rango que la red física de la VM anfitriona. Esto facilita la comunicación entre los contenedores y hace posible el establecimiento del enlace \textbf{N2} (SCTP) entre el NGRAN y el AMF.

\subsubsubsection{DB}

\begin{lstlisting}[style=yamlstyle, caption={Configuración del MongoDB en Docker Compose}, label=lst:docker-db]
services:
  db:
    container_name: mongodb
    image: mongo:3.6.8
    command: mongod --port 27017
    expose:
      - "27017"
    volumes:
      - dbdata:/data/db
    networks:
      macvlan_net:
        ipv4_address: 172.18.0.50
        mac_address: "22:e5:63:00:49:85"
        aliases:
          - db
\end{lstlisting}

\section{Despliegue de switches BMv2 con INT-MD}
Los switches BMv2 se han desplegado utilizando GNS3, los ncuales manejaran el trafico SCTP y GTP-U entre el NGRAN (gNB) y el Core 5G (AMF y UPF) insertando metadatos INT-MD en los paquetes de datos. Estos metadatos reunen los siguienrtes parametros de telemetria de red:
\begin{itemize}
    \item Switch ID
    \item Puerto de entrada
    \item Puerto de salida
    \item Latencia por salto
    \item Ocupación de cola
    \item Reporte de Congestión
\end{itemize}

\subsection{Switch INT Source}
El switch INT-Source (bmv2-1) fue construido para insertar metadatos INT-MD en el tráfico SCTP y GTP-U proveniente del NGRAN (gNB) hacia el Core 5G (AMF y UPF). Como el protocolo SCTP es quien transporta el protocolo NGAP en la interfaz N2, Todos los paquetes de attach por parte del usuario y el establecimiento de session con el AMF llevaran los metadatos INT-MD insertados por el switch INT-Source. De igual manera, todos los paquetes de datos del usuario transportados por GTP-U en la interfaz N3 entre el gNB y el UPF llevaran los metadatos INT-MD insertados por el switch INT-Source.

A continuación se detallan los bloques de codigo P4 implementados en el switch INT-Source para la inserción de metadatos INT-MD en el tráfico SCTP y GTP-U:

parser MyParser(packet_in packet,
            out headers hdr,
            inout metadata meta,
            inout standard_metadata_t standard_metadata) {

    state start {
        packet.extract(hdr.ethernet);
        // Inicializacion de metadata INT
        meta.ingress_port = standard_metadata.ingress_port;
        meta.ingress_ts = (bit<32>)standard_metadata.ingress_global_timestamp;
        meta.is_int_packet = 0;
        meta.is_ngap_traffic = 0;
        meta.is_gtp_u_traffic = 0;
        meta.traffic_type = 0;  // 0=other, 1=NGAP, 2=GTP-U
        meta.should_insert_int = 0;
        transition select(hdr.ethernet.etherType) {
            0x0800: parse_ipv4;
            default: accept;
        }
    }
    // ... estados intermedios omitidos ...
    state parse_udp {
        packet.extract(hdr.udp);
        meta.transport_src_port = hdr.udp.src_port;
        meta.transport_dst_port = hdr.udp.dst_port;

        // Deteccion de trafico GTP-U (interfaz N3)
        transition select(hdr.udp.dst_port == GTP_U_PORT || 
                          hdr.udp.src_port == GTP_U_PORT) {
            true: parse_gtp_u;
            false: accept;
        }
    }
    state parse_gtp_u {
        packet.extract(hdr.gtp_u);
        meta.is_gtp_u_traffic = 1;
        meta.traffic_type = 2;  // Tráfico GTP-U
        transition accept;
    }
    state parse_sctp_common {
        packet.extract(hdr.sctp);
        meta.transport_src_port = hdr.sctp.src_port;
        meta.transport_dst_port = hdr.sctp.dst_port;

        // Deteccion de trafico NGAP (interfaz N2)
        if (hdr.sctp.dst_port == NGAP_PORT) {
            meta.is_ngap_traffic = 1;
            meta.traffic_type = 1;  // Trafico de senalizacion
        }
        transition parse_sctp_chunk;
    }

    // ... resto de estados omitidos ...
}

El bloque de código \ref{lst:int-parser} reune los estados mas relevantes del parser P4 implementado en el switch INT-Source. En el estado \textit{start}, se inicializan las variables de metadata interna del switch, como el puerto de ingreso, timestamp de ingreso y flags para identificar si el paquete es INT, NGAP o GTP-U. Luego, en el estado \textit{parse\_udp}, se extrae la cabecera UDP y se almacenan los puertos de origen y destino en la metadata interna del switch. Si el puerto de destino o origen coincide con el puerto GTP-U (2152), se transiciona al estado \textit{parse\_gtp\_u} para extraer la cabecera GTP-U y marcar el paquete como tráfico GTP-U en la metadata interna del switch. De manera similar, en el estado \textit{parse\_sctp\_common}, se extrae la cabecera SCTP y se verifica si el puerto de destino coincide con el puerto NGAP (38412), marcando el paquete como tráfico NGAP en la metadata interna del switch. En caso contrario, se acepta el paquete sin marcarlo como tráfico NGAP o GTP-U.

        standard_metadata.egress_spec = egress_port;
    }

    // Tabla 1: Verifica si la IP origen está configurada para INT
    table int_source_ip_table {
        key = {
            hdr.ipv4.srcAddr: lpm;
        }
        actions = {
            int_source_action;
            NoAction;
        }
        size = 1024;
        default_action = NoAction();
    }

    // Tabla 2: Verifica el tipo de tráfico para las IP marcadas para INT
    table int_traffic_type_table {
        key = {
            meta.traffic_type: exact;
        }
        actions = {
            int_source_action;
            NoAction;
        }
        size = 1024;
        default_action = NoAction();
    }

    table ipv4_lpm {
        key = {
            hdr.ipv4.dstAddr: lpm;
        }
        actions = {
            forward_action;
            NoAction;
        }
        size = 1024;
        default_action = NoAction();
    }

    apply {
      //Aquí es donde empieza la magia
        meta.switch_id = 1;
        if (hdr.ethernet.isValid() && hdr.ipv4.isValid()) {
            // Primero: Verifica si la IP origen está configurada para monitoreo INT y es válida.
            if (hdr.ipv4.srcAddr != 0) {  
                int_source_ip_table.apply();
            }

            // Segundo: Si la IP origen coincide, verifica si el tipo de tráfico es NGAP o GTP-U
            if (meta.should_insert_int == 1) {
                if ((hdr.ipv4.protocol == PROTOCOL_SCTP && hdr.sctp.isValid()) ||
                    (hdr.ipv4.protocol == PROTOCOL_UDP && hdr.udp.isValid())) {
                    int_traffic_type_table.apply();
                } else {
                    // Sí no es SCTP o GTP-U, limpia el flag INT
                    meta.should_insert_int = 0;
                }
            }

            // Aplica el reenvío
            ipv4_lpm.apply();

            // Inserta cabeceras INT si el flag está en 1
            if (meta.should_insert_int == 1) {
                do_insert_int();
            }
        }
    }
}      
\end{lstlisting}
Como el bloque de código \ref{lst:int-ingress} Contiene comentarios en cada sección, no es necesario detallar su funcionamiento. En su lugar, es preciso destacar que la razón por la que se decidió implementar una tabla para especificar las IPs de origen que se le va a aplicar INT y otra tabla para verificar el tipo de tráfico (NGAP o GTP-U) es para optimizar el rendimiento del switch. De esta manera, se reduce la cantidad de paquetes que pasan por la lógica de inserción INT, ya que solo los paquetes que cumplen ambos criterios serán procesados para la inserción de metadatos INT-MD. Esto mejora la eficiencia del switch aportando mas flexibilidad para agregar mas IP de gnb en el futuro sin afectar el rendimiento del switch.

\subsection{Switch INT Transit}
El INT-Transit (bmv2-2) fue construido para procesar los paquetes con metadatos INT-MD insertados por el switch INT-Source. Su función principal es actualizar los campos de metadatos INT-MD en cada salto, como el egress port, egress timestamp, hop latency y queue occupancy. 
Teniendo en cuenta que los aspectos generales sobre la definición de constantes, cabeceras, parser, egress y deparser son similares a los del switch INT-Source, se detallan únicamente las diferencias clave en la implementación del switch INT-Transit.

\subsubsection{Parser}
A diferencia del switch INT-Source, el INT-Transit tiene la capacidad para procesar paquetes que ya contienen metadatos INT-MD insertados.

\begin{lstlisting}[language=C++,
    basicstyle=\ttfamily\footnotesize,
    keywordstyle=\color{blue!70!black}\bfseries,
    commentstyle=\color{green!50!black}\itshape,
    stringstyle=\color{red!80!black},
    directivestyle=\color{blue!70!black}\bfseries,

    frameround=tttt,

    captionpos=b,

    framexleftmargin=12pt,
    literate=
      {á}{{\'a}}1 {é}{{\'e}}1 {í}{{\'i}}1 {ó}{{\'o}}1 {ú}{{\'u}}1

    label=lst:int-transit-parser]
parser MyParser(packet_in packet,
                out headers hdr,
                inout metadata meta,
                inout standard_metadata_t standard_metadata) {
    state start {
        packet.extract(hdr.ethernet);
        meta.ingress_port = standard_metadata.ingress_port;
        meta.ingress_ts = (bit<32>)standard_metadata.ingress_global_timestamp;
        meta.md_blocks_extracted = 0;
        meta.is_int_packet = 0;
        transition select(hdr.ethernet.etherType) {
            0x0800: parse_ipv4;        // IPv4 sin INT (no esperado en transit)
            0xFA: parse_int_shim;      // Paquete con INT (esperado)
            default: accept;
        }
    }
    // Parsing de cabeceras INT
    state parse_int_shim {
        packet.extract(hdr.int_shim);
        meta.is_int_packet = 1;        // Marcar como paquete INT
        transition parse_int_header;
    }

    state parse_int_header {
        packet.extract(hdr.int_header);
        // Calcular cuántos bloques de metadatos extraer
        meta.md_blocks_extracted = hdr.int_header.hop_ml - 
                                   hdr.int_header.remaining_hop_cnt;
        transition parse_int_metadata;
    }

    state parse_int_metadata {
        // Extraer bloques de metadatos existentes
        // SW1 envió 1 bloque, así que extraemos int_md[0]
        packet.extract(hdr.int_md[0]);
        transition parse_encapsulated_protocol;
    }

    state parse_encapsulated_protocol {
        transition select(hdr.int_shim.next_proto) {
            0x0800: parse_encapsulated_ipv4;  // IPv4 encapsulado
            default: accept;
        }
    }

    state parse_encapsulated_ipv4 {
        packet.extract(hdr.ipv4_inner);
        transition select(hdr.ipv4_inner.protocol) {
            PROTOCOL_SCTP: parse_encapsulated_sctp_common;
            PROTOCOL_UDP: parse_encapsulated_udp;
            default: accept;
        }
    }
    // ... estados adicionales para procesar UDP/GTP-U o SCTP omitidos ...
}
\end{lstlisting}

Al recibir el paquete, el parser del switch INT-Transit primero verifica el EtherType. Si detecta que es \textbf{0xFA} (TYPE\_INT), extrae la cabecera INT Shim y marca el paquete como un paquete INT en la metadata interna del switch.
Luego, extrae la cabecera INT Header y calcula cuántos bloques de metadatos ya han sido insertados por switches anteriores, almacenando este valor en la variable \texttt{md\_blocks\_extracted} de la metadata interna del switch.
Una vez que se conocen los bloques existentes, el parser procede a extraer esos bloques de metadatos INT-MD. Finalmente, extrae el paquete original (IPv4, SCTP/UDP, GTP-U) que está encapsulado dentro de las cabeceras INT.

control MyIngress(inout headers hdr,

        }

}

A este punto, el switch INT-Transit procesa todos los paquetes con cabeceras INT válidas, independientemente del protocolo encapsulado (NGAP o GTP-U). Antes de agregar un nuevo bloque, revisa si hay espacio disponible en la cabecera INT para insertar más metadatos, verificando el campo \texttt{remaining\_hop\_cnt}. Si este valor es mayor que cero, procede a insertar un nuevo bloque de metadatos INT-MD en la siguiente posición disponible del array \texttt{int\_md[]}.

Un aspecto importante a destacar es que el switch INT-Transit añade \textbf{32 bytes adicionales} por cada salto procesado. Para fines de esta prueba de concepto, solo se cuenta con un switch INT-Transit (SW2).

\subsection{Switch INT Sink}
El switch INT-Sink (bmv2-3) o INT-Destination, representa el último nodo en la ruta de telemetría INT, el cual se encarga de recibir los paquetes, clonarlos, enviar una copia al servidor de recolección y luego reenviar el paquete original hacia su destino final, que en este caso es el 5G Core a traves de los Routers Core.

Para fines de optimizacion, se detallan solo los aspectos claves.

\subsubsection{Parser}
El parser del switch INT-Sink debe extraer todos los bloques de metadatos INT-MD que fueron insertados por los switches anteriores en la ruta. A diferencia del INT-Transit que solo necesita extraer los bloques anteriores, el INT-Sink debe procesar la pila completa para poder enviarla al servidor de recolección.

Como se mostró en la topologia \ref{sec:topologia_int}, el parser del INT-Sink debe extraer:
\begin{itemize}
    \item \textbf{int\_md[0]}: Metadatos insertados por SW1 (INT-Source)
    \item \textbf{int\_md[1]}: Metadatos insertados por SW2 (INT-Transit)
    \item \textbf{int\_md[2]}: Metadatos que serán completados por SW3 (INT-Sink) en Ingress/Egress
\end{itemize}

                    hdr.int_md[2].hop_latency = 0;
                    hdr.int_md[2].egress_timestamp = 0;
                    hdr.int_md[2].queue_occupancy = 0;
                    hdr.int_md[2].congestion_notification = 0;
                    hdr.int_md[2].reserved1 = 0;
                    hdr.int_md[2].reserved2 = 0;

                    hdr.int_header.remaining_hop_cnt =

                int_sink_table.apply();
            }
        }

        // Forwarding del paquete original hacia su destino
        if (hdr.ipv4_inner.isValid()) {
            ipv4_lpm.apply();
        }
    }

\subsubsection{Egress}
El control Egress del switch INT-Sink implementa la lógica más compleja de todos los switches INT, debido a que procesa tres tipos de paquetes:

\begin{enumerate}
    \item \textbf{Paquete clonado} (\texttt{instance\_type == 1}): Destinado al servidor de recolección, debe mantener todas las cabeceras INT intactas.
    \item \textbf{Paquete original hacia el servidor} (\texttt{egress\_port == 9}): También mantiene las cabeceras INT.
    \item \textbf{Paquete original hacia el destino final}: Debe eliminar todas las cabeceras INT para restaurar el paquete a su formato original.
\end{enumerate}

La acción \texttt{strip\_int\_headers()} es exclusiva del INT-Sink y se encarga de eliminar todas las cabeceras INT, restaurando el EtherType original y desencapsulando el paquete.

            hdr.int_md[2].ingress_timestamp;
        hdr.int_md[2].queue_occupancy = 
            (bit<32>)standard_metadata.enq_qdepth;

        hdr.int_md[2].setInvalid();
        hdr.int_md[3].setInvalid();
        hdr.int_md[4].setInvalid();
        hdr.int_md[5].setInvalid();
        hdr.int_md[6].setInvalid();
        hdr.int_md[7].setInvalid();

        key = {
            standard_metadata.egress_port: exact;
        }

            strip_int_headers;

        }

        default_action = NoAction();

            update_int_metadata();

            } else {

                egress_control.apply();

\subsubsection{Deparser}
El deparser del switch INT-Sink es similar al del INT-Transit, emitiendo todas las cabeceras en orden. Sin embargo, su comportamiento varía según el procesamiento en Egress:

    """Parsear paquete INT desde bytes L2.
    
    Nota: INT usa EtherType 0x00FA que es < 0x0600, por lo que
    muchas herramientas lo clasifican como IEEE 802.3 length.
    Debemos parsear los bytes directamente.
    """
    raw_data = bytes(pkt)
    if len(raw_data) < 14:
        return None
    
    # Extraer cabecera Ethernet (14 bytes)
    dst_mac = ':'.join(f"{b:02x}" for b in raw_data[0:6])
    src_mac = ':'.join(f"{b:02x}" for b in raw_data[6:12])
    type_or_len = struct.unpack('>H', raw_data[12:14])[0]
    
    # Verificar EtherType INT
    if type_or_len != 0x00FA:
        return None
    
    offset = 14
    
    # Parsear INT Shim Header (6 bytes) - big-endian
    shim_data = raw_data[offset:offset+6]
    shim_type, shim_reserved, shim_length, shim_next_proto = \
        struct.unpack('>BBHH', shim_data)
    print(f"[INT] Shim: type={shim_type}, length={shim_length}, "
          f"next_proto=0x{shim_next_proto:04x}")
    offset += 6
    
    # Parsear INT Header (7 bytes en teoría, pero puede tener padding)
    header_data = raw_data[offset:offset+7]
    b0 = header_data[0]
    b1 = header_data[1]
    version = (b0 >> 4) & 0x0F
    hop_ml = header_data[2]
    instruction = struct.unpack('>H', header_data[3:5])[0]

      {Á}{{\'A}}1 {É}{{\'E}}1 {Í}{{\'I}}1 {Ó}{{\'O}}1 {Ú}{{\'U}}1
      {ñ}{{\~n}}1 {Ñ}{{\~N}}1,
    caption={Extracción y validación de metadatos INT-MD}, 
    label=lst:int-script-metadata]
def parse_int_metadata_correct(md_data, hop_number):
    """Parsear un bloque de metadatos INT (28 bytes).
    
    Implementa auto-detección de endianness y recuperación
    heurística de errores comunes.
    """
    if len(md_data) < INT_MD_LEN:
        print(f"[ERROR] Bloque de metadatos muy corto: {len(md_data)} bytes")
        return None
    
    # Auto-detectar endianness
    be = _decode_int_md(md_data, '>')  # Big-endian
    le = _decode_int_md(md_data, '<')  # Little-endian
    be_score = _score_int_md(be)
    le_score = _score_int_md(le)
    chosen = le if le_score >= be_score else be
    endian_used = 'le' if chosen is le else 'be'
    
    switch_id = chosen["switch_id"]
    ingress_port_id = chosen["ingress_port_id"]
    egress_port_id = chosen["egress_port_id"]
    hop_latency_field = chosen["hop_latency_field"]
    queue_occupancy = chosen["queue_occupancy"]
    ingress_timestamp = chosen["ingress_timestamp"]
    egress_timestamp = chosen["egress_timestamp"]
    
    # Calcular latencia desde timestamps si están disponibles
    ts_latency = None
    if ingress_timestamp != 0 and egress_timestamp != 0:
        ts_latency = (egress_timestamp - ingress_timestamp) & 0xFFFFFFFF
    
    # Recuperación heurística de errores comunes
    # En algunos casos, los campos se desplazan debido a errores
    # de alineación: hop_latency=0, egress_ts=0, pero queue_occupancy
    # contiene un timestamp válido
    recovered = False
    if (hop_latency_field == 0 and egress_timestamp == 0 
        and ingress_timestamp > 1_000_000 
        and queue_occupancy > 1_000_000):
        # Intercambiar campos desplazados
        candidate_delta = (ingress_timestamp - queue_occupancy) & 0xFFFFFFFF
        if candidate_delta < 1_000_000:
            ingress_timestamp, egress_timestamp = queue_occupancy, ingress_timestamp
            queue_occupancy = 0
            ts_latency = (egress_timestamp - ingress_timestamp) & 0xFFFFFFFF
            recovered = True
    
    # Usar timestamp-derived latency si está disponible
    hop_latency_used = ts_latency if ts_latency is not None else hop_latency_field
    
    # Convertir microsegundos a milisegundos
    hop_latency_ms = hop_latency_used / US_TO_MS
    ingress_timestamp_ms = ingress_timestamp / US_TO_MS
    egress_timestamp_ms = egress_timestamp / US_TO_MS
    
    print(f"[DEBUG] Hop {hop_number}: switch={switch_id}, "
          f"ingress={ingress_port_id}, egress={egress_port_id}, "
          f"queue={queue_occupancy} packets, latency={hop_latency_ms:.3f}ms "
          f"[{endian_used}]")
    
    return {
        "switch_id": switch_id,
        "ingress_port_id": ingress_port_id,
        "egress_port_id": egress_port_id,
        "hop_latency": hop_latency_used,
        "hop_latency_ms": hop_latency_ms,
        "queue_occupancy": queue_occupancy,
        "ingress_timestamp": ingress_timestamp,
        "egress_timestamp": egress_timestamp,
        "hop_number": hop_number,
        "endian": endian_used,
        "recovered": recovered
    }
\end{lstlisting}

\subsubsection{Almacenamiento en InfluxDB}
Una vez extraídos y validados los metadatos de todos los saltos, el script almacena la información en InfluxDB utilizando dos mediciones (measurements) diferentes:

\begin{enumerate}
    \item \textbf{int\_metrics}: Almacena metadatos individuales de cada salto (por-hop)
    \item \textbf{int\_path\_metrics}: Almacena métricas agregadas de toda la ruta (end-to-end)

def handle_packet(pkt):
    """Manejar paquetes INT entrantes"""
    metadata_blocks = parse_int_packet(pkt)
    if not metadata_blocks:
        return
    
    # Construir representación de la ruta
    switch_ids = [f"SW{md['switch_id']}" for md in metadata_blocks]
    path_str = " -> ".join(switch_ids)
    print(f" PATH: {path_str}")
    
    # Almacenar cada bloque en InfluxDB
    for md_block in metadata_blocks:
        json_body = [{
            "measurement": "int_metrics",
            "tags": {
                "switch_id": md_block["switch_id"],
                "ingress_port": md_block["ingress_port_id"],
                "egress_port": md_block["egress_port_id"],
                "hop_number": md_block["hop_number"],
                "parser_version": PARSER_VERSION,
                "parser_endian": md_block["endian"],
            },
            "fields": {
                "hop_latency_us": md_block["hop_latency"],
                "hop_latency_ms": md_block["hop_latency_ms"],
                "queue_occupancy_packets": md_block["queue_occupancy"],
                "ingress_timestamp_us": md_block["ingress_timestamp"],
                "egress_timestamp_us": md_block["egress_timestamp"],
                "ingress_timestamp_ms": md_block["ingress_timestamp_ms"],
                "egress_timestamp_ms": md_block["egress_timestamp_ms"],
            },
            "time": int(time.time() * 1e9)  # Nanosegundos
        }]
        client.write_points(json_body)
    # Calcular y almacenar latencia end-to-end
    # IMPORTANTE: No restar timestamps entre switches diferentes
    # porque cada BMv2 tiene su propio dominio de tiempo.
    # En su lugar, sumar las latencias individuales de cada salto.
    e2e_latency_us = sum(md["hop_latency"] for md in metadata_blocks)
    e2e_latency_ms = e2e_latency_us / US_TO_MS
    path_json_body = [{
        "measurement": "int_path_metrics",
        "tags": {
            "path": path_str,
            "hop_count": len(metadata_blocks),
        },
        "fields": {
            "end_to_end_latency_us": e2e_latency_us,
            "end_to_end_latency_ms": e2e_latency_ms,
            "total_hops": len(metadata_blocks),
        },
        "time": int(time.time() * 1e9)
    }]
    client.write_points(path_json_body)
    print(f" E2E latency (sum): {e2e_latency_ms:.3f}ms ({e2e_latency_us}us)")
\end{lstlisting}

Un aspecto crucial a destacar es el cálculo de la latencia end-to-end. Dado que cada instancia de BMv2 (cada switch) tiene su propio dominio de tiempo independiente, \textbf{no es válido restar timestamps entre switches diferentes}. Por ejemplo, \texttt{SW3.ingress\_timestamp - SW1.ingress\_timestamp} puede resultar en valores negativos o sin sentido. Por ello, la latencia end-to-end se calcula como la \textbf{suma de las latencias individuales} de cada salto, que es la métrica correcta para medir el tiempo total que el paquete pasó en la infraestructura de red.
